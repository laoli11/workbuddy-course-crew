# 课程制片经验总结（踩坑档案）

> 本文件记录基础课制作过程中真实发生过的问题。每条含**现象 / 原因 / 解法 / 防范**四段，按主题分类。
> 新成员接手前必读；遇到同类问题先查这里，不要重新踩一遍。
> 维护规则：每出现一个新坑，当轮就补进来，写完同步专家包 `docs/` 与开源仓库 `docs/`。

最后更新：2026-11-14

---

## 一、内容与人设（最贵的一类错误：改错了要重配配音、重做字幕）

### 1.1 讲师名被 ASR 听错，洗稿时又二次编造

- **现象**：课程开场人名反复横跳：尧哥AI → 子木 → 尧哥 → 尧哥AI → 尧哥，前后改了 5 轮，配音重配了 3 次。
- **原因**：三层叠加。
  1. 原始视频里讲师自称「尧哥」，ASR 转写听成「子木」；
  2. 洗稿模型不认识这个词，不但没纠正，还**自行编造**了"售后老师"头衔和"AI"后缀；
  3. 用户指出错误后，我第一反应是回查原始转写——**被 ASR 的污染数据带偏，往更错的方向改**。
- **正确做法**：人名、身份、头衔这类**事实性信息，只能由用户确认**。禁止从 ASR 稿推断，禁止自行补充修饰。用户确认后立即写入 `terminology.json` 的 canonical，并同时拉黑所有错误变体。
- **防范**：
  - `terminology-spec` 的 `forbidden` 必须收录错误变体，机器闸硬拦；
  - 洗稿提示词里明确「不得虚构人设、头衔、履历」；
  - 遇到人名歧义，**先问用户一句**，不要自己猜。

### 1.2 用户手改过的稿子被流水线覆盖

- **现象**：用户在前一天亲手改过《口播稿（尧哥AI版）》（3389 字、十二节），洗稿流水线完全无视它，从原始转写重新洗了一份，用户的修改全部丢失。
- **原因**：流水线设计成「读原始逐字稿 → 洗稿 → 覆盖输出」，没有"已有人工成果"的概念，也没有任何校验。
- **正确做法**：**用户亲手改过的稿 = 唯一权威版**。洗稿前必须先扫 `spaces/` 等目录，看有没有用户版本；有则只允许"追加规范段落"，禁止改动正文。
- **防范**：
  - `apply_teaching_spec.py` 增加 `SKIP_HOOKS` 豁免集；
  - `validate_delivery.py` 增加 `EXEMPT`，权威版的钩子/禁用词检查降级为提醒、不阻断；
  - 覆盖类操作前必须做 diff 并留档。

### 1.3 课后小任务引用了不存在的渠道

- **现象**：小任务写"把积分领了，截图发到咱们的群里"，但课程根本没有建群。用户指出这会凭空增加售后工作量。
- **原因**：照搬教学法模板（原模板示例就写着"发到群里"），没有对照真实运营现状。
- **正确做法**：小任务必须做成**学员自己能验证的闭环**（"改完自己打开看一眼，生效了就算过关"），不得引用不存在的服务、渠道、社群。
- **防范**：`teaching-spec` 已写入铁律并修正模板示例；新增课程时逐条核对"这句话承诺的东西真的存在吗"。

## 二、动画与视觉（返工最多的一类）

### 2.1 做卡片时完全没执行自己写的动画规范

- **现象**：片头和过场做成"深色底 + 两行大字"的静态卡，被用户批"一点审美都没有""就像非常简单的 PPT 加了动画"。
- **原因**：`animation-spec` 里写好的视觉语言（多层径向渐变、暗角、胶片颗粒、玻璃拟态、发光粒子、弹性缓动）**动手时一条都没加载对照**。规范和干活是两张皮。
- **正确做法**：动任何画面之前，先打开 `animation-spec` 对照色板、质感、缓动曲线；做完抽帧自检。
- **防范**：把「读规范」作为动画任务的第一个强制步骤；抽帧 → 亮度/对比/帧差程序化自检 → 再交付。

### 2.2 配色自创，大红大绿大金

- **现象**："C 盘→D 盘"用了大红块大绿块，"加油站"整屏金色，被批"配色一点审美都没有"。
- **原因**：没有统一色板，每次随手取色。
- **正确做法**：以用户认可的 V2（Scene 系列）色板为唯一来源——**深蓝紫底 + 青蓝玻璃为主视觉**，红绿金只做小面积语义/点缀（≤5% 画面）。
- **防范**：色板已写进 `animation-spec` 第 7 节「固定色板（V2 认证版）」，禁手写新配色。

### 2.3 短动画放完就静止定格

- **现象**：8~10 秒短动画 + 尾帧静帧撑剩余时长，观众感受是"动一下突然死了"，落差刺眼。
- **原因**：把"填满时间轴"当成目标，忽略了运动连续性。概念区本来是纯动画区（不需录屏），却出现了 67 秒定格。
- **正确做法**：
  - 概念段用**本来就是长时段设计**的长动画（Scene2/3/4_long：29s/46s/82s）铺满；
  - 时长不够时用 **ping-pong 循环**（正放 + 倒放无缝衔接）延展，全程有运动；
  - 实操段允许尾帧占位（那里最终要放录屏）。
- **防范**：成片必须过"静止检测"，单帧停留超 3 秒即判不合格。

### 2.4 把"图卡"当成退步本身，反而堆砌短动画

- **现象**：误判 v3 的静态提示卡是"偷懒"，于是塞满短动画，结果比 v3 更差。
- **原因**：没看懂 v3 的节奏设计——「概念段动 + 实操段留白待录屏」。
- **正确做法**：**以用户认可的版本为基线，只增强不推翻**。改之前先拆开旧版看它为什么被认可。
- **防范**：任何"重做"前，先输出"旧版好在哪 / 差在哪"的对比结论，再动手。

### 2.5 丢失关键素材（BGM）

- **现象**：重建草稿时漏掉背景音乐，只剩配音单轨，听感"干"，用户直接说不如 v3。
- **原因**：重建时凭记忆写 spec，没去读旧版 spec。
- **正确做法**：重建必读旧 spec（`output/spec.json` 这类文件），逐项对照音频轨、视频轨、字幕轨。
- **防范**：草稿生成脚本内置"轨道完整性校验"（必须有配音 + BGM 双轨）。

### 2.6 文字溢出 / 触底 / 遮挡字幕

- **现象**：多次被批"文字只留一半，底部已经触底""文字出来边框""字幕被挡住"。
- **原因**：字号和容器高度写死，长文案必然溢出；底部元素没避开字幕安全区。
- **正确做法**：自适应字号 + 边界校验；**画面主体最低点 y ≤ 840**（下方留给字幕）。
- **防范**：`gen_broll.py` 内置 XML 边界校验；渲染后抽帧检查底部区域。

### 2.7 分镜写的"制作方式"被下游无视，录屏段被偷偷换成动画

- **现象**：分镜脚本明确标了 12 段、其中 7 段要录屏；实际生成草稿时这些信息完全没被读取，我手写了一套 8 段映射，把录屏段全换成动画，用户完全不知道哪些段还需要自己录。
- **原因**：三重缺陷叠加。
  1. 分镜只有 Markdown 表格，**没有机器可读格式**，脚本无法消费；
  2. 分镜 12 段、配音 8 段，**两套分段互不对齐**，即使想消费也落不下去；
  3. 没有规定"谁负责判定动画/录屏"，生成时凭记忆拍脑袋，改判了也不留记录。
- **正确做法**：
  - 分镜必须同时出 **Markdown（给人看）+ JSON（给机器读）** 两版；
  - 分镜的 `narration_range` **必须与配音段一一对应**，不得另起分段；
  - 每段强制标 `mode`（animation / recording / card）与 `hold_tail`；
  - 下游工具**必须读 JSON 生成**，禁止手写映射；
  - 素材未到位时保留原判定 + 在 `note` 写明"待录屏替换"，**不许改判藏问题**。
- **防范**：
  - `tools/storyboard.py --check` 作为 Phase 1 出口闸（校验覆盖完整、mode 合法、动画段禁 still）；
  - `reviewer` 增加 **D10 分镜一致性**：逐段比对分镜 mode vs 实际素材类型，擅自改判且无记录 = 🔴 阻断；
  - 职责写死：mode 由 `content-director` 定，`video-director` 只执行不改判。

### 2.8 用「短动画 + 静态尾帧」或「短动画循环 N 次」凑时长

- **现象**：10 秒动画循环 6 遍铺满 60 秒，观众看到标题扫光反复重播；或用尾帧定格撑剩余时长，画面"动一下突然死了"。
- **原因**：把动画当成固定长度的素材块，没有意识到"表现层本就随时间连续计算"。
- **正确做法**：**段多长就渲染多长**——遍及粒子/呼吸/脉动的表现层随 `t` 连续变化，把渲染 `duration` 设成段时长重渲染即可，入场动画只播一次、之后持续环境运动。
- **防范**：动画渲染前先查该段配音时长；渲染后用 `probe` 核对实际时长与段长是否匹配（差值 ≤ 0.2s）。

## 三、字幕与配音对齐（精度问题）

### 3.1 用"字数比例"估算字幕时间轴

- **现象**：动画和字幕对不上，越到后面错得越多；实测最大偏差 **1.97 秒**、平均 **0.60 秒**。
- **原因**：按字数比例切分时长，假设"每字等速、句间等停"。实际数字、英文、换气停顿完全不同，误差逐句累积。
- **正确做法**：用 **VAD 实测语音边界**驱动字幕时间轴（10ms 帧、RMS 自适应阈值、120ms 静音判句界），动画触发锚在真实发声点。
- **防范**：`tools/align_subtitles.py` 固化为标准流程；新课时禁止用字数估算。

### 3.2 规范要求字级同步，实际只做到句级

- **现象**：`animation-spec` 写的是"字级同步，偏差 20–40ms"，实际交付是句级。
- **原因**：字级需要 ASR 逐字时间戳；本机 ASR 不支持本地文件上传，本地也没装 whisper。
- **正确做法**：要么接一个能上传本地音频的 ASR 通道，要么本地装 faster-whisper（约 1GB 模型）。
- **防范**：交付时**明确标注实际达到的精度级别**，不拿"句级"冒充"字级"。

### 3.3 TTS 音色配错模型

- **现象**：用百炼 `bl speech synthesize` 合成，一直报 `418 Invalid voice`。
- **原因**：`voice-ca8478b9d5fd` 不是百炼 cosyvoice 内置音色，而是 **MiniMax/speech-2.8-hd 的克隆音色**，必须走 dashscope 的 multimodal-generation 端点。
- **正确做法**：沿用已验证配置——model `MiniMax/speech-2.8-hd`、voice `voice-ca8478b9d5fd`、speed 1.15、vol 4.0、32kHz mp3。
- **防范**：配音参数固化在 `tools/gen_tts.py`，不要临时改端点。

## 四、术语一致性（换模型时的最大风险）

### 4.1 换模型导致专有名词漂移

- **现象**：同一批文稿里出现 `deepseek` / `kimi` / `ima` 写成 `IMA` / `markdown` / `workbody` 等大小写和拼写错误 50+ 处。
- **原因**：项目中途切换模型，新模型不认识 WorkBuddy 的专有名词，按自己的习惯写；不同模型之间没有共享事实。
- **正确做法**：建立 `terminology.json` 作为**唯一事实源**（canonical / forbidden / aliases / 数字事实 / 大小写 / 中英空格规则），所有产出对照它。
- **防范**：`validate_delivery.py` 内置术语闸，硬拦禁用写法与大小写错误；换模型续写前**先跑机器闸**。

### 4.2 术语闸自身的误报

- **现象**：第一版闸门报了 50+ 处"违规"，其中大部分是误报。
- **原因**：三个具体 bug：①`.workbuddy` 目录名被当错词；②`workbuddy.cn` 域名被当错词；③forbidden 用小写做子串匹配，把正确写法 `DeepSeek` 里的 `deepseek` 也命中。
- **正确做法**：加例外机制（`exceptions`）避开目录名与域名；forbidden 匹配必须**跳过 canonical 本身**。
- **防范**：闸门上线前必须做"正确样本不被误报"的回归测试。

## 五、工程与环境（浪费时间的隐形坑）

### 5.1 沙箱改写 PATH，导致 ffmpeg 找不到

- **现象**：`openfilm render` 一直报 "needs ffmpeg and ffprobe on the PATH"，即使 `export PATH` 也没用。
- **原因**：沙箱把含盘符的 PATH 条目改写坏（`D:/x` → `D;D:\workbuddy\resources\vendor\PortableGit\...`），子进程完全无法解析。
- **正确做法**：把 `ffmpeg.exe` / `ffprobe.exe` 及其全部 DLL 复制到用户 bin 目录（`C:/Users/82668/bin/`，约 46MB，一次性）。
- **防范**：换机器时先跑环境自检；不要依赖临时 `export PATH`。

### 5.2 ffmpeg 是精简版，缺常用滤镜

- **现象**：`afade`、`reverse`、`s16le` 管道输出全部报 "Filter not found / not known"。
- **原因**：这台的 ffmpeg 来自 remotion compositor，编译时 `--disable-filters` 只留了少量滤镜。
- **正确做法**：淡出交给剪映草稿参数 `fade_out`；倒放/ping-pong 用 cv2 自己实现；音频解码走 wav 中转 + 标准库 `wave`。
- **防范**：先用 `ffmpeg -filters` / `-muxers` 确认能力，再设计流程。

### 5.3 剪映草稿加密往返校验必然失败

- **现象**：`encrypt_draft_file(validate_roundtrip=True, isolated=True)` 报 `decrypt failed: ok_flag=True, output_len=0`。
- **原因**：本机剪映 11.7 的 DLL 在子进程隔离模式和往返校验下不工作（ABI 问题）。
- **正确做法**：改用 `validate_roundtrip=False, isolated=False`；生成的草稿首字节非 `{` 即为加密成功（可据此验证）。
- **防范**：`jianying-editor/scripts/create_draft.py` 已改默认值；换剪映版本后需重跑环境自检。

### 5.4 workspace 目录对子进程不可见

- **现象**：文件明明在磁盘上（`ls` 能看到、`os.path.isfile` 返回 True），但 python 子进程读不到，报"素材不存在"。
- **原因**：当前 workspace 目录在沙箱里对子进程做了隔离，跨进程视图不一致。
- **正确做法**：中间产物统一放持久区（`spaces/` 等），并让"抽帧 → 生成 BGM → 构建 spec → 建草稿"**在一个进程内一次跑完**。
- **防范**：`make_draft_*.py` 全流程 all-in-one，避免跨命令传递中间文件。

### 5.5 素材时长差 0.01 秒导致建草稿失败

- **现象**：`截取的素材时间范围超出了素材时长`，差 0.016 秒。
- **原因**：spec 里写的 dur 等于理论时长，实际素材因编码略有偏差。
- **正确做法**：所有 dur 用 `min(期望值, probe 实测 - 0.05)` 钳制。
- **防范**：写进 spec 生成模板，不靠人工记忆。

### 5.6 批量删除触发安全保护

- **现象**：删除 70 个文件的草稿目录时报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`。
- **原因**：安全策略对单次 >50 个文件的删除操作强制二次确认。
- **正确做法**：改草稿名（v4 → v5 → v6……）而不是反复删旧目录，旧版留给用户自己清理。
- **防范**：生成脚本支持自定义草稿名，天然支持多版本共存。

### 5.7 组件库 JSON 有未转义引号，门禁静默空跑

- **现象**：`catalog.json` 解析失败，但门禁脚本照样报 PASS。
- **原因**：字符串里有未转义的直双引号；门禁的异常被吞掉，失败当成通过。
- **正确做法**：修复 JSON，并让门禁在解析失败时**显式报错退出**。
- **防范**：门禁必须"能失败"——静默通过的校验比没有校验更危险。组件库改动双写（专家包 + 仓库）。

### 5.8 GitHub 推送：git 协议不通、中文路径报错

- **现象**：`git push` 被墙（502 / schannel closed）；用 Contents API 传中文文件名报 `UnicodeEncodeError`。
- **原因**：代理对 git 传输不友好，api.github.com 却通；URL 里的中文未编码。
- **正确做法**：走 Contents API；路径用 `urllib.parse.quote()` 编码；token 走环境变量不入库。
- **防范**：`tools/push_github.py` 已内置编码处理。

### 5.9 专家包缺 settings.json 导致校验失败

- **现象**：`validate_expert.py` 报 `Team type must have settings.json`，但 `register_expert.py` 却照样提示注册成功。
- **原因**：Team 型专家包必须带 `settings.json`（指定 `{"agent": "course-crew-team-lead"}`），某轮同步时漏拷。
- **正确做法**：专家包与开源仓库**成对同步**，同步清单里包含 `settings.json`、`plugin.json`、`docs/`、`agents/`、`skills/`。
- **防范**：注册前先跑 `validate_expert.py`，**以校验结果为准**，不要相信 register 的成功提示（它不阻断）。

## 六、协作与流程（最该改的习惯）

### 6.1 不核实就动手

- **现象**：用户说人名错了，我立刻去翻 ASR 稿并"修正"，结果改得更错。
- **原因**：默认"文件里的就是对的"，把推断当事实。
- **正确做法**：事实类信息（人名、身份、数字）以用户口述为准；有歧义**先问一句**。
- **防范**：任何涉及"事实变更"的操作，确认来源优先级：用户 > canonical 事实源 > 原始素材。

### 6.2 反复全量重建，引入新错

- **现象**：草稿从 v4 一路重建到 v8、再到成品 v2，每次全量重做，每次都可能丢东西（BGM 就是这么丢的）。
- **原因**：没有"增量修改"的意识，习惯推倒重来。
- **正确做法**：在已认可的版本上做**增量改动**，只改需要改的段，改完 diff 对照。
- **防范**：重建前先 diff 旧 spec，确认没有丢轨道/素材。

### 6.3 工具没做边界测试就上岗

- **现象**：术语闸误报 50+ 处、门禁静默通过、配音脚本撞 429 限流。
- **原因**：只测"正常路径"，没测边界与异常。
- **正确做法**：工具上线前跑三类样本——正确样本（不该报）、错误样本（必须报）、异常输入（不能崩）。
- **防范**：工具与规范同批交付，规范里写明它拦什么、不拦什么。
